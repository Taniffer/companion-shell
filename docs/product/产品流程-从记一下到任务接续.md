# 从“记一下”到伙伴接续

产品讨论稿 · 2026-11-16

本稿把已讨论的人类需求转成具体使用行为，暂不决定技术实现。继续保留：伴随式、厂商原生工具、多角色、客户端互通、可迁移记忆，以及轻记录入口和完整交互终端的区分。

## 一、产品需要完成的闭环

用户可以不做分类就留下信息；之后找得到、用得上；明确交办时能进入具体任务；事情结束后保留成果和经过核实的经验。

保存资料、形成任务、做出决定和积累技能之间没有强制升级关系。一条片段可以一直只是资料；一句明确要求也可以直接形成任务。用户不需要为每条收藏安排一个将来必须处理的日期。

## 二、以一天的使用为例

以下为产品情景示例，不代表这些操作已经发生或功能已经实现。

| 时刻 | 用户行为 | 产品应有的行为 | 用户当下的负担 |
|---|---|---|---|
| 刷到资料 | 看到一个营地，点“记一下” | 留住实际内容、来源与时间，简短回执，可撤销 | 无需选伙伴和项目 |
| 继续工作 | 回到 Codex 做研究 | 保持当前研究焦点；新的营地资料安静保留 | 无需处理新收藏提醒 |
| 发起请求 | 在飞书说“把我最近记的营地比较一下” | 找到相关片段，关联具体出行任务，交给合适帮手；只询问会改变下一步的必要条件 | 不重复粘贴资料 |
| 看看进展 | 在手机终端打开任务 | 直接看到完成内容、依据、卡点、下一步和成果 | 不需要再问 AI 一遍“做到哪了” |
| 中途改变 | 说“改成当天来回” | 更新本次出行决定，调整受影响的安排，保留仍有用的资料 | 不重建整个计划 |
| 以后接续 | 再次安排出行或更换模型 | 取用相关共同背景和可靠经验，不默认沿用上一次出行条件 | 少解释，也能随时纠正 |

## 三、“记一下”完成的是保存，而非立即开工

默认建议：

- 先记录实际取得的内容，保留出处和当时背景。
- 做轻量的去重、内容识别和可能关联，不阻塞用户离开。
- 不强迫指定角色、项目、标签和期限。
- 不因保存资料自动展开长篇分析、创建待办或启动外部行动。
- 用户可以补一句“交给产品帮手研究”“今晚提醒我”，这才表达了额外的行动意图。
- 当前拿不到正文时如实标明只留住链接或截图，不能把摘要生成成功冒充原文已完整保存。

后台看到的近期线索与用户主动记下的片段保留不同含义。主动记录表示值得保留，不直接表示赞同、偏好或决定。

## 四、资料应该在合适的时候回来

单独的资料收件箱可以存在，但不能把每天清空收件箱变成新的义务。优先通过三种方式找回：

1. 自然提问：用户说“前几天那个可以车宿的地方”，能沿相关线索找回，并显示来源。
2. 进入事情：打开某次出行，能看到与之相关的片段和过去决定。
3. 请求帮助：角色准备工作时取用相关资料，并用很短的说明展示采用了什么背景。

没有实际使用价值的新发现先安静保留；与用户已经交办的事情有关、确实影响决定的信息，才进入该任务或约定的提醒。

默认不把所有新资料标成未读、不每日自动催清理，也不假设每条资料未来都需要用上。

## 五、交互终端围绕三类需要展开

### 看现在

优先展示用户近期正在推进或明确关注的事情。每件事首先回答：已经完成什么、现在卡在哪里、接下来要做什么、是否需要用户决定、成果在哪里。

状态可以是进行中、等待资料、需要决定、已产出待查看、已完成或暂时搁置。没有可测量依据时不虚构百分比。查看状态不应额外发起一次模型对话。

### 继续一件事

打开任务时带回本次目标、现行决定、未决项、接续位置和必要资料。用户能够看清当前正在处理哪件事、由谁负责，也能改变方向。

同一任务可以跨终端延续。仅仅切换飞书、自研客户端或原生桌面窗口，不应产生新的任务；真正提出另一个目标时，再建立独立焦点。

当“继续那个”有多个合理候选时，给出少量具体事项选择，避免默默串到错误任务，也避免让用户寻找内部编号。

### 找某位伙伴

允许直接找量化、产品或生活帮手进行自由讨论。交流可以暂时不绑定任务，明确出现需要推进的目标时再提取出来。

角色页保留长期分工、当前参与事项、最近合作和适用经验。角色不只是头像，也不因为拥有很多任务就必须携带全部历史。

## 六、多角色协作首先帮助用户减少协调

每件事可以有一位主负责帮手，再按需要找其他帮手协助。角色交接要带上目标、现行约束、已完成内容、相关成果和下一步。

例如，量化帮手整理数据口径，产品帮手依据这条定义制作看板。用户关心的是口径是否一致、成果是否能用，不需要手动当传话人，也不必围观所有角色之间的中间沟通。

用户可以展开查看参与者与依据；默认只呈现对理解进度和做决定有帮助的信息。系统不为展示“多 Agent”而把每个小步骤都变成一位新角色。

## 七、记忆更新要尊重含义

| 用户表达或记录 | 应怎样理解 |
|---|---|
| “看到这个，留一下” | 保存片段，不表示认同或决定 |
| “这次预算只按这个范围考虑” | 当前事项的约束，不提升为长期个人偏好 |
| “以后成果都给我稳定入口” | 可复用的交付偏好，带适用范围与来源 |
| “上次那个条件不算了” | 更新对应的现行理解，保留历史变化 |
| 助手说“已经完成” | 执行报告，仍与实际验证证据区分 |

用户能够直接用自然语言纠正，不需要先学会记忆分类。记忆修正影响相关任务时，应让这些地方采用新理解，而不是让用户到每位角色处重复修改。

## 八、技能积累的实际收益

完成任务后，先记录做法和效果，再判断它是否值得复用。候选技能需要说明何时适用、用过哪些例子、有什么限制。只在合适的任务里取用。

角色的成长体现在更少重复解释、更少返工、更可靠的接续和交付。记忆与技能允许修正、合并和退役，不以数量增长作为成功标准。

## 九、飞书和独立客户端共享同一段合作经历

飞书适合沿用用户的消息习惯；独立客户端承载更完整的任务、伙伴、资料、记忆和成果组织。两种终端可以各自独立作为日常入口，不要求使用者同时开两个界面。

基础接续应一致：选择具体事项、补充要求、查看状态、回答问题、取得成果。独立客户端再提供更细的整理与查看能力。信息不会因为来自某个终端就永久被锁在该终端中。

## 十、第一轮产品验证只验证完整的一件事

建议用一个生活情景走完：

记录一条真实资料 → 在另一个终端找回 → 与已有事项关联 → 由一位帮手推进 → 直接查看进度 → 中途改主意 → 得到可访问的成果 → 下次适当复用。

另一条验证情景是量化帮手与产品帮手共同完成一个研究看板，确认用户不必重复搬运资料，也不会把两个领域的全部上下文混在一起。

通过这些情景判断产品是否值得反复使用，再扩展入口数量和自动感知范围。
