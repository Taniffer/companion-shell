# 页面与交互流程：从简单助手到专业协作

产品体验讨论稿 · 2026-11-17 · 不讨论技术选型与实现

## 一、这轮确定的产品方向

对人，助手是一位熟悉自己、替自己操心的秘书；对参与工作的 Agent，她承担公司老板的组织职责：接目标、定优先级、选择人手、分配任务、协调依赖、检查交付、控制资源投入。

用户只需要能说清“我希望怎样”，不必先学会组织团队。只需要一个简单助手的人，可以始终只和她相处。专业能力、团队和页面深度按真实事情展开，不要求用户选择简易版或专业版。

助手是否找人、找谁、找多久，由助手在已有委托与资源范围内判断。用户可以表达“这件事别搞复杂”“找专业的人看看”，也可以直接与某位专业伙伴长期合作。增减人手不应改变用户熟悉的主要入口。

本稿中的场景、页面内容和交付状态均为产品示例，不代表实际执行。配套交互示意只演示页面如何接续。

## 二、人的需求如何落到页面上

| 人的真实需要 | 产品应提供的体验 | 主要页面 |
|---|---|---|
| 懒得组织 | 一句话交代，助手自行判断是否分工 | 助手首页 |
| 懒得记住 | 随手留下，相关时找回；未完成的事有人继续跟 | 轻入口、任务页、例行事项 |
| 懒得重讲 | 换入口仍知道当前在做哪件事 | 任务页、专业对话 |
| 懒得盯着 | 直接看真实状态、卡点、下一步 | 首页简报、事情列表 |
| 懒得筛材料 | 有推荐、有差异、有依据，可直接作出选择 | 决定卡、成果页 |
| 想自己深入 | 一步找到专业伙伴或原生工作对话 | 任务参与者、对话列表 |
| 想保留掌控感 | 能暂停、改主意、接管、纠正，并看到影响 | 所有相关页面 |
| 想被理解 | 一次纠正可以在相关工作中生效 | 关于我的理解、任务决定记录 |

用户在不同时间需要不同深度：随手记录、简短交代、扫一眼进度、深入讨论、亲自修改。复杂度应随当下意图展开；同一个人无需切换产品模式。

## 三、轻入口、主要导航与完整页面

轻入口独立于完整终端，默认只是“记一下”。完整终端的主要导航稳定为：助手、事情、对话、更多。第一次只看到助手和输入框；其他入口保持容易找到，未使用的功能不展示空面板。

“更多”承载资料、关于我的理解、例行事项、专业伙伴、技能与经验、设备和来源、设置。桌面可使用侧栏，手机可使用底部导航；名称与内容含义保持一致。

| 页面／界面状态 | 主要解决什么 | 从哪里进入 | 可以接到哪里 |
|---|---|---|---|
| 首次打开 | 无需先配置一家公司，直接说第一句话 | 第一次使用 | 助手首页；有需要再补资料来源 |
| 记一下与回执 | 保存眼前内容，不打断当前活动 | 小图标、分享入口、快捷动作 | 短暂回执；可撤回或打开资料 |
| 助手首页 | 交代事情、查看与自己有关的简报 | 默认入口、通知、返回助手 | 任务、决定卡、成果、相关对话 |
| 事情列表 | 找到当前和过去的事项 | 主要导航 | 任务详情、领域／项目、例行事项 |
| 任务详情 | 恢复一件事，理解进度并继续推进 | 首页、列表、对话中的任务链接 | 专业对话、秘书对话、材料、成果 |
| 专业对话 | 和具体专业伙伴深入交流 | 任务参与者、最近对话、伙伴页 | 同一任务、成果、继续由秘书协调 |
| 对话列表 | 找到原来的交流，无需记住它属于谁 | 主要导航、近期对话 | 原对话及其相关事项 |
| 决定卡与比较展开 | 让用户完成确实需要自己的取舍 | 首页、任务、相关对话 | 原地处理，复杂比较再展开 |
| 成果查看 | 直接使用交付，围绕结果继续修改 | 首页成果、任务、对话链接 | 打开成果、继续修改、交回秘书 |
| 领域／项目 | 恢复持续关心的一类事情 | 事情分组、搜索、相关链接 | 当前任务、历史成果、领域记忆 |
| 资料 | 找回见过和记下的内容 | 更多、任务材料、自然提问结果 | 原文／截图、关联任务、用于新请求 |
| 关于我的理解 | 查看和纠正助手如何理解自己 | 更多、回答中的背景引用 | 纠正、限制范围、查看出处、迁移 |
| 例行事项 | 掌握持续委托和定时工作 | 更多、事情、自然交代 | 查看计划、最近结果、修改或暂停 |
| 专业伙伴 | 按需要直接找人，了解分工 | 更多、任务参与者 | 对话、参与事项、适用经验 |
| 技能与经验 | 了解已验证的方法及其适用范围 | 更多、某次工作的经验引用 | 查看例子、修订、合并、停用 |
| 设备、来源与设置 | 知道信息从哪里来、覆盖到何时 | 更多、缺资料时的上下文入口 | 调整连接、范围、通知与委托约定 |

这是完整页面库存，不是要求用户经常巡视的菜单。决定卡、材料、成果通常在任务内直接使用；专业伙伴和技能也不需要成为普通用户的日常管理工作。

## 四、助手首页：从一段对话自然长出总览

### 没有复杂工作的日常

默认显示熟悉的助手、一句简短开场、输入框，以及少量最近对话或可继续的事项。用户说“把这段话写得自然一点”，直接得到结果。这类已经当场结束的交流，不必创建长期任务，也无需招一位写作员工。

页面不展示空的待办、员工数量、项目指标或能力目录。首次使用无需填写完整个人档案。补充背景应发生在确实用得上时。

### 已有事情在推进

在对话附近增加一段简报，按内容出现：需要你决定、正在推进、已交付可用、影响当前事情的变化。没有内容的部分不占位置。首页可以概括多件事，也可以只保留一张与当前焦点有关的卡。

每张卡优先给出事情名称、变化或现状、建议或下一步。动作使用明确文字，例如“按建议继续”“查看进展”“打开页面”“直接找量化伙伴”，不依赖用户再问一遍状态。

用户可以固定最关心的事情。随着使用增加，保持入口位置稳定；只改变相关内容，不频繁移动主要导航。所有其他事项始终能从“事情”找到。

### 首页输入的去向

自由交代默认为与秘书交流。输入前可以带有清楚的事项标记，例如“继续：量化监控页”，此时发言落在该任务。用户主动开始另一件事时，建立另一个焦点；不让一条无限长对话承担全部生活。

“随便聊聊”保留为交流。“帮我持续跟进”才形成需要后续承担的委托。助手可以做可修正的判断，避免让用户每次先选择消息类型。

## 五、事情列表与领域页：按事情找，比按员工找更直接

事情列表用简洁的分组列表呈现。默认先显示正在推进、等待你、已交付待使用；暂停和历史在后面。每条包含目标简称、最新变化、下一步和更新时间。可按需要找某领域或项目，不默认铺开看板和所有子任务。

一件持续的研究或软件项目可以拥有多个任务。领域／项目页聚合当前事情、稳定口径、重要成果和相关资料。用户无需先建文件夹树，助手可以提出或形成可撤销的归并。

角色和项目保持不同：量化伙伴可能参与多项研究；“量化监控页”也可能同时需要量化与产品伙伴。页面以目标组织，再按参与者深入。

## 六、任务详情：三处衔接的中心

进入任务先恢复四件事：目标是什么，当前有效决定是什么，做到哪了，下一步由谁做。常见内容顺序为：

1. 任务名称与当前状态，附最后已知更新时间。
2. 当前目标、关键约束和最新变化；刚返回时可见“离开后变了什么”。
3. 需要用户决定的内容；没有待决定事项时不显示。
4. 已完成内容、当前卡点、下一步；有证据或交付可直接打开。
5. 参与者；只有一位助手时可直接显示“由助手处理”，多人时按需展开。
6. 进展、对话、材料与成果。详细过程折叠，默认展示里程碑而非每次工具动作。

主要动作包括继续交代、找参与者聊、打开成果、暂停。修改目标、暂存、归档和查看完整过程放在次级操作中。

任务页是可直接交互的工作页面：能在此比较选项、调整顺序、补一份材料、修改约束；不必把所有操作都写成聊天指令。

### 真实状态与下一步

| 状态 | 页面必须说明 | 合理的主要动作 |
|---|---|---|
| 正在处理 | 已完成什么、当前步骤、后续交付 | 看进展、补充要求 |
| 等待条件 | 缺什么、谁在解决、后续如何恢复 | 补资料、查看处理安排 |
| 需要你判断 | 具体取舍、推荐、影响、依据 | 按建议继续、看差异 |
| 已交付 | 成果在哪里、已做的验证、剩余限制 | 打开、继续修改 |
| 暂停 | 停在哪里、保留了什么、如何继续 | 恢复、归档 |
| 状态待确认 | 最后已知状态、时间、正在如何核实 | 查看已知结果、稍后接续 |

完成状态需要交付依据。已交付与用户已查看是不同状态，不要求每次都点正式验收。持续委托保留在例行事项中，单次结果可以完成，不把常驻工作挂成永远无法结束的普通任务。

## 七、专业对话：直接深入，同时保持任务连贯

任务内的专业对话顶部固定表达三个事实：正在和谁聊、属于哪件事、这位伙伴负责哪部分。桌面可以在任务侧边展开，深入时再打开完整对话；手机进入子页面，返回原任务位置。视图形式改变，交流对象与任务范围不变。

例如：

量化伙伴 · 量化监控页 · 负责指标口径。

主要返回动作是“查看任务”和“交给助手继续协调”。进入已有工作时接续同一条专业交流；不因为从另一个入口点进来就另建一份重复任务。

### 发言怎样改变工作

明确的本次指令，如“这次先用静态样例，只保留回撤、换手和更新时间”，更新当前任务的有效约束。对话下出现简短回执：“已更新本任务；产品伙伴将按此制作样例。”可查看变化、修正或撤回。

讨论和决定需要区分。“先聊聊另一种可能，别改现有安排”留在探索范围。对含义会影响处理方向的模糊表达，给少量具体解释供选择，避免无声改变目标，也避免逐条确认每句话。

“以后所有成果都给我稳定入口”可以影响长期协作约定；“这次只给我简版”只影响当前事项。当前任务的要求不能无声覆盖其他研究或全局偏好。

### 从角色直接开始聊天

用户从量化伙伴页直接进入时，可以选择最近事项，也可以自由讨论。明确谈到一个现有任务就接上它；提出独立新目标时形成新的任务关联，给简短回执并允许修正。无需先填写任务表单。

一个角色可拥有多条有范围的对话。对话列表帮助找回，任务列表帮助判断进度，两者相互链接。

## 八、首页、任务与专业对话之间的衔接规则

三处围绕同一件事显示不同深度的信息。任务承载目标与进展，聊天承载交流，秘书承载面向用户的整理和协调。

| 用户动作 | 当前页面发生什么 | 其他地方怎样接上 |
|---|---|---|
| 首页点“查看进展” | 进入该任务，落在最近变化或待决定处 | 保留首页返回位置 |
| 任务点量化参与者 | 打开此任务的量化对话 | 任务名称和负责范围持续可见 |
| 专业对话修改要求 | 显示解释与简短更新回执 | 任务采用新要求，秘书重新协调受影响部分 |
| 返回助手 | 回到相关任务的秘书交流或首页简报 | 给出变化与下一步，无需用户重讲 |
| 在任一处处理决定 | 原地显示已处理及接下来的动作 | 其他入口同一决定同步变为已处理 |
| 在成果上要求修改 | 保留所指成果与版本，进入原任务 | 形成后续工作，已交付版本仍能找回 |
| 在手机补充要求 | 显示当前事项与发送对象 | 电脑接续同一要求，不重复开工 |
| 从原生工作对话继续 | 保留实际工作中的交流与成果线索 | 总览能恢复相关任务进展；具体支持范围后续验证 |

三条可检查的不变规则：切换页面不复制任务；切换交流对象不丢当前范围；同一决定只需处理一次。返回时还应保留草稿、选中成果和阅读位置。

对话中的背景更正应尽快接回相关事项，但页面要如实表达更新过程。“已收到”“正在调整其他工作”“相关安排已更新”不是同一种完成状态。

## 九、一段完整的专业协作流程

### 1. 交代

用户在助手首页说：“帮我做一个方便查看的量化监控页。”

助手先结合已有资料形成当前目标；若确实需要分工，自行安排量化伙伴整理口径，产品伙伴制作页面。用户得到的是处理计划和后续交付，无需操作招聘界面。

### 2. 看进度

隔一段时间打开首页，看到：“指标口径已整理；第一版需要确定用静态样例，还是接入实时数据。建议先做静态样例，便于确认信息布局。”

用户可以直接采用建议，也可以进入任务看依据。该范围确实影响后续工作时才提出选择；若已有明确约定，直接按约定推进。

### 3. 直接找专家

用户进入量化伙伴对话说：“这次先用静态样例，只保留回撤、换手和更新时间。”

伙伴解释这次保留的指标与边界，记录本次要求。任务移除已经回答的选择，更新当前范围，受影响的页面工作随之调整。

### 4. 回到秘书

用户回首页，秘书简报：“这版已按静态样例安排，量化口径已经确定，产品伙伴接着制作。暂时没有需要你处理的事。”

无需把刚才的对话再发一遍。旧提醒不再要求用户重复选择。

### 5. 使用与继续修改

页面交付后，首页出现“打开监控页”。成果页标明静态样例的范围、当前版本和已做的检查。用户说“把更新时间放到最上面”，在同一任务接续修改。

### 6. 长期接续

如果用户希望持续维护，助手将其放入相应项目或例行委托。后来换电脑、换工作伙伴时，仍能找回有效口径、成果和下一步；不会默认沿用已经废弃的约束。

## 十、一天里更轻的使用方式

| 时刻 | 用户只做什么 | 产品怎样服务 |
|---|---|---|
| 早上 | 打开助手，问一句当天安排 | 按已知内容简短回答；无复杂工作就保持简单 |
| 工作中 | 请她改一段文字 | 当场给结果；通常不建长期任务、不增加角色 |
| 刷内容时 | 点一下“记一下” | 保存实际取得的材料并回执，用户继续刷 |
| 午间 | 说“上次那几个营地找给我” | 带来源找回，先满足找资料的意图 |
| 下午 | 顺手看一眼研究任务 | 看到最新变化、卡点与下一步，不需再次问进度 |
| 路上 | 用手机回复一个关键选择 | 同一事项继续，电脑不再重复催促 |
| 晚上 | 说“今天这些事你接着安排，研究先放着” | 调整优先级和暂停范围，留下可恢复的位置 |
| 下次 | 说“继续那个监控页” | 带回目标、有效决定、当前成果和下一步 |

助手不必把所有互动组织成任务，也不把全部收藏变成待办。用户持续轻用，可以始终拥有一位简单助手。

## 十一、由助手决定招人，具体意味着什么

先判断自己是否能直接完成；需要专业能力时优先找已有伙伴；短期复杂工作可找临时协作者；反复出现且需要长期背景的工作，再形成稳定专业伙伴。人手应该可以合并、退场和再次调用，历史成果与经验不随员工退场而消失。

这些是产品组织原则，不意味着角色越多能力越强。增加人手必须解决实际问题：专业差异、可独立验证的工作，或有价值的并行。简单改写无需成立写作部门。

默认只告诉用户与交付有关的分工变化，例如“这件事我请量化伙伴看口径，产品伙伴做页面”。详细人员安排在任务参与者和伙伴页可见。用户可以直接找人、固定常用伙伴或要求少分工。

助手作为老板还需负责资源投入与交付质量：避免重复劳动，控制无意义返工，判断什么时候停止研究，保留可复用成果。新增伙伴本身不扩大用户已经给出的预算与行动委托。

## 十二、决定卡与成果页需要足够的 GUI

决定卡先解释具体问题，再给建议和影响；用户可以采用建议、修改条件、看差异或稍后处理。对比复杂时展开成可读的比较页面，保留推荐依据与原始材料。

简单选择使用按钮，排序使用可调整列表，改参数使用字段，审阅成果使用对应预览。聊天用于表达新意图和复杂背景，GUI 用于识别当前状态、比较和直接操作。

成果页优先展示可使用的成果；补充当前版本、适用范围、验证情况和来源。修改针对明确对象，附上被讨论的段落、图表或版本。用户不必回长聊天里寻找附件。

决策与成果都属于原任务。多入口出现的是同一件事的不同呈现，不生成多个待办。已使用、已查看和已完成的含义保持区分。

## 十三、资料、记忆、例行事项与技能怎样进入日常

资料优先通过自然提问、相关任务与原出处找回，资料库是兜底入口。每条材料说明取得了什么：完整正文、截图或仅有链接。后台观察线索与用户主动保存保留不同含义。

关于我的理解区分用户明确表达、任务内决定和系统推测，并保留时间、适用范围和出处。用户说“这次只是临时安排”即可修正范围；相关任务看到修正后的理解。材料可以存在而不进入长期记忆。

例行事项展示持续委托的目的、执行安排、可运行条件、上次结果、下次预计时间，以及修改和暂停入口。没有运行条件时说明原因，避免仅靠一个定时标签制造正在服务的错觉。

技能与经验展示适用情境、已核实的方法、案例与限制。日常由助手维护，用户需要时查看。成功经验可以候选沉淀，不能把每次偶然成功都加成长期规则。

## 十四、手机、飞书和电脑怎样衔接

轻记录、简短交代和完整处理在各入口均有对应能力。手机以单列和子页面承载相同事项，电脑可以并排查看任务与对话。飞书承接消息、简报和简短选择，复杂比较可进入完整终端。

发言前显示当前对象与事项；用户可以顺着已有话题说话。含糊的“那个”有多个合理候选时，给少量带名称和近期线索的选项。跨入口保持已知状态一致，离线或等待更新时显示最后已知时间。

同一用户已经处理过的选择不应在其他设备继续催促。默认由秘书集中需要用户处理的消息，专业伙伴仍可在用户直接交流的上下文中回复；避免多人、多设备同时重复汇报。

厂商原生 Desktop／CLI 继续是专业工作场所。此处定义接续体验，具体哪些状态能被接入应在技术阶段逐项核实。

## 十五、容易破坏省心体验的边界情况

| 情况 | 应有的处理 |
|---|---|
| 只是随口想想 | 保留讨论，不立刻派活或改变已定目标 |
| 一句话混了两件事 | 形成可分开的事项关联，给可纠正的简短回执 |
| 明确改变当前任务 | 更新有效要求，解释受影响部分，保留旧版可追溯 |
| 新要求影响其他工作 | 由助手协调；需要真正取舍时再带建议询问 |
| 不同入口出现相互矛盾的要求 | 展示具体冲突和建议，先继续不受影响的部分 |
| 伙伴失败或暂时不可用 | 助手先处理接续，必要时汇报影响、替代安排与可用成果 |
| 设备或来源不可用 | 标明覆盖与最后已知状态，不编造已看到或已完成 |
| 用户说先停 | 清楚暂停哪个范围，停止追问，保留恢复位置 |
| 推测的记忆有误 | 低成本纠正，在相关范围生效，允许查看来源 |
| 收藏越来越多 | 安静保留与按需找回，不形成每日清空义务 |

## 十六、客观依据与设计推导

以下来源帮助解释设计取舍，不构成本产品效果已经得到验证的证据。

| 研究／设计原则 | 它提供的视角 | 本稿的具体推导 |
|---|---|---|
| 认知卸载，Risko 与 Gilbert | 外部工具可改变任务的信息处理需求 | 记录、找回、记住后续和恢复工作需要一起设计 |
| 协调理论，Malone 与 Crowston | 协调涉及活动之间的依赖 | 老板型助手接住分工、交接、冲突和收尾 |
| 渐进呈现，Nielsen | 优先展示常用选项，按需提供专门能力 | 单助手也完整可用；团队和详细管理按需展开 |
| 识别优于回忆，Budiu 的界面设计解释 | 有线索的识别比凭空回忆更容易 | GUI 直接展示状态与选项，减少重复询问和回想 |
| 混合主动交互，Horvitz | 自动服务需考虑意图不确定性、注意力与直接控制 | 秘书主动安排，用户随时直达专业伙伴、停止或修正 |
| 恢复计划实验，Leroy 与 Glomb | 在其研究条件中，准备恢复计划有助于减轻中断带来的注意力残留 | 任务返回时提供当前目标、停靠位置与下一步 |
| 人机交互准则，Amershi 等 | 易调用、易修正、结合近期交互与谨慎适应 | 明确范围、可撤回更新、渐进形成对用户的理解 |

## 十七、如何验证这个产品确实服务了人的懒

先分别观察只需一个助手的人，以及有多个长期事项的人。前者应当不学习团队管理也能持续获得帮助，后者应当不靠手动传话维持协作。

验证以下具体行为：第一次交代能否直接开始；是否需要用户先选角色；隔天恢复任务要花多久；直接找专业伙伴后是否还需向秘书复述；同一决定有没有重复询问；成果是否容易打开和继续修改；记忆纠正是否减少后续误解；委托后新增了多少监督与设置工作。

用户的总心力包括记住、找回、解释、选择、协调、监督、纠正，以及维护产品本身。只有总负担确实下降，扩充角色和功能才有意义。角色数、消息数、停留时长和保存量不应单独作为成功标准。

这轮不启用采集、同步、例行工作或真实 Agent 调度，只明确产品行为和页面关系。
