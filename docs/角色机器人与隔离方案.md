# 角色创建、独立机器人与隔离方案

版本提示：本文保留原始规划与历史边界。当前 0.2 的实现范围见 [V2 实现说明](V2实现说明.md)，实际通过与待验收项目见 [验证记录](验证记录.md)。
更新日期：2026-11-17。本文记录下一版需求与设计，当前运行中的 0.1 仍是一个飞书机器人、四种固定工作配置。

## 产品要求

每个长期角色拥有独立身份，可绑定独立飞书应用机器人，具有自己的名称、职责、记忆范围和任务列表。用户能直接私聊这个角色，也能让秘书协调。默认只需要秘书；专业角色由持续需要推动创建。

一个角色可以处理多个事项，每个事项保留独立的执行会话。临时分析、一次检查、一个子任务不自动变成一只长期机器人。机器人身份长期保留，事项可以结束、归档和迁移。

秘书是能亲自完成各类工作的全能助手，也是受委托团队的老板，对目标和最终交付负责。她保留直接做量化研究、软件实现和生活安排的能力。专业角色负责持续投入、独立上下文和领域积累，秘书可以委派、检查、接管、重组和收回工作。

秘书拥有角色管理能力：判断是否需要新角色，提出招募建议，创建内部角色，分配职责和初始资料，绑定机器人入口，查看工作进度，解雇或合并角色。她能授予的权限来自用户预设范围，创建新角色不会使原有权限自动扩大。

## 自然招募与组织调整

秘书根据用户已经共享的对话和事项，判断同类需求是否持续增加、是否反复解释相同背景、是否值得保留专门的经验。一次性需求可以直接处理或临时分工；适合长期投入时，再提出具体招募建议。

建议应说明角色解决什么问题、接哪些已有事项、使用哪些资料，以及预计投入。例如：“你最近经常做策略研究，要不要招一位量化助理，长期记录数据口径和实验结果？你仍然可以直接找我。”用户同意后，创建、配置、资料交接与入口接入由助手完成。

同样，角色长期闲置、职责重叠或对应阶段已经结束时，秘书可以提出合并或解雇建议。用户也可以直接说“把这位助理撤掉，工作并回你”。不要求用户自己搬运资料、重新解释背景或手工改任务归属。

## 解雇与合并回秘书

解雇是一段完整交接：先核对正在执行和等待处理的工作，为未结束的工作安排唯一接管方；保留原事项编号、历史、成果、来源与进展；再把角色积累迁入秘书管理的相应领域资料中。

| 积累 | 合并规则 |
|---|---|
| 未完成任务 | 交给秘书或明确指定的其他角色，继续原目标和原进展 |
| 已完成任务与成果 | 保留历史和来源，归属转移，不重新生成一份冒充原交付 |
| 事实、偏好和决策 | 去重并保留出处；矛盾项保留差异，不把助手推测升级成用户事实 |
| 领域经验和技能 | 作为可检索、可按需装载的领域资产保留，不全部塞进秘书的常驻上下文 |
| 文件与原始资料 | 保留实际文件及引用，交接适用权限，不扩大对其他角色的共享范围 |
| 机器人和连接 | 核对交接完成后移除相应外部入口，撤销不再使用的专属连接或凭证 |

秘书接回的是这项工作的责任和全部可用积累，当前对话仍只装载相关内容。角色可以增减，用户不用担心撤掉机器人就失去过去的成果。

角色管理应呈现“建议招募—筹备—在职—交接中—已并回/已归档”等真实状态。删除外部机器人、移除入口和保留用户工作资产分别记录，只有已实际完成的操作才报告成功。

## 当前 0.1 的实际隔离

| 层次 | 当前行为 | 尚未具备的能力 |
|---|---|---|
| 飞书身份 | 同一机器人通过命令切换助手、量化、产品和生活配置 | 每个角色独立的机器人身份与连接 |
| 角色创建 | 四种配置固定在程序中；秘书能委派专业子事项 | 动态创建、修改、绑定和归档长期角色 |
| 对话 | 以事项绑定独立 Codex thread；同一角色可有多条事项 | 独立机器人收件箱和角色级长期对话管理 |
| 记忆 | 个人共同记忆、指定事项记忆和项目范围字段 | 角色私有记忆与角色间共享授权 |
| 资料 | 初始上下文只带选入资料；专业子事项的检索限于分配资料 | 顶层私人角色间的资料域隔离；当前顶层私人事项可检索个人资料库 |
| 任务接口 | 凭证限于本事项及其子事项，专业子事项不能读取兄弟事项 | 基于长期角色身份的统一授权策略 |
| 文件、工具和账户 | 共用 Windows 账户与已登录 Codex，工具和技能沿用原环境 | 操作系统或执行器强制的角色权限隔离 |

因此，当前具备任务与上下文的逻辑隔离，不能描述为角色级安全沙箱。更换提示词、分开文件夹或更换飞书机器人头像，都不能限制一个拥有全盘文件工具的执行环境。

## 下一版的隔离规则

| 对象 | 默认归属与共享方式 |
|---|---|
| 机器人身份 | 绑定唯一长期角色；消息收件、回信、去重和任务归属包含机器人身份 |
| 角色记忆 | 角色私有；用户明确标为共同偏好的内容进入共享层 |
| 事项上下文 | 一事一份；同角色其他事项按相关性检索，不自动合并全部聊天 |
| 项目资料 | 由项目成员范围决定；角色加入该项目后获得相应资料 |
| 原始记录 | 记录时可留待整理；交办时分配给事项或角色，按既定规则自动流转 |
| 共享事实 | 带来源、适用范围和修订记录；获准角色可共同使用 |
| 工作文件 | 独立角色工作区，事项再分目录；硬性读写边界必须由执行环境执行 |
| 工具与账号 | 每个角色有明确授权；不同机器人凭证单独管理，不写入模型记忆 |
| 技能 | 每个角色保留自己的技能目录与适用经验，按当前事项选择少量相关技能 |

角色之间的隔离主要约束专业角色的横向访问。秘书在用户的持续委托范围内拥有受管理团队的任务、记忆和成果访问权，可以按需深入细节、接管工作和完成解雇交接；日常只加载与当前目标相关的信息。用户明确设为仅自己可见或不向秘书共享的特殊资料，仍遵循该限制。

例如，量化伙伴保留策略研究过程，产品伙伴保留软件需求与实现记录；“回答先给结论”可以作为共同偏好。两者需要协作时，传递该事项相关的研究摘要、数据定义与文件，避免整份领域历史被灌进另一方上下文。

## 协作方式

角色之间通过内部事项交接协作，飞书负责向用户展示，不依靠机器人在群里反复互相发消息。每次交接保留发送角色、接收角色、目标、可用资料、预期交付和结果。

共享范围已明确时自动交接，无需每条资料询问一次。角色请求范围之外的数据或能力时，系统呈现具体缺口。模型提出请求不等于系统已经授予权限。

用户直接和专业伙伴聊时，这段交流归专业角色和当前事项；秘书收到该事项约定的进度与交付，用户随时可以回到总事项继续协调。

## 自主创建与飞书开通分开处理

内部角色创建可以由秘书自动完成，包括身份、职责、记忆域、任务列表和最小权限。独立飞书机器人的开通受飞书平台流程约束。

2026-11-18 调研修正：飞书官方 Node SDK 已提供 `registerApp`，用户扫码或打开链接确认后可创建应用、返回凭据，并申请增量权限、事件与回调。不能继续用旧 FAQ 推断“官方不能扫码创建”。官方 V7 另有配置、提交发布接口，但明确限制应用创建渠道；SDK 创建的具体应用能否适用，仍需按真实应用验证。群自定义 webhook 机器人不能承担可独立私聊和收取用户消息的角色。[官方 SDK](https://github.com/larksuite/node-sdk/blob/main/README.zh.md#一键创建应用)，[完整接入调研](feishu-v2/飞书接入调研.md)。

创建、配置、发布以及撤下入口由助手选择合适的执行方式完成：有经过验证且获准使用的 API 时使用 API，界面操作步骤通过浏览器完成。备用机器人池可以作为加快接入的选项，不作为用户必须手工准备的前提。登录和平台必须由用户完成的步骤在实际遇到时呈现具体事项；其余配置与交接由助手承担。可用的名字、头像、权限和发布状态应以平台实际结果为准。

角色状态必须区分“内部已创建”“等待飞书开通”“已绑定可聊”和“已归档”，不能在没有真实飞书身份时显示为机器人已创建。每只机器人分别验证用户绑定，回信必须由原接收机器人发送，避免身份和事项串线。

## 执行环境的强制边界

角色资料接口应按角色和事项验证权限，而不只依靠提示词。文件和工具的硬隔离还需要厂商执行器支持并强制相应限制，或采用独立操作系统账户、容器、虚拟机、独立设备等环境。

若仍共用有广泛文件权限的 Windows 账户与 Codex 环境，产品只能说明已经实现逻辑隔离。不能以外围接口有权限校验为依据，声称模型无法读取其他角色的本地文件。界面应能说明当前采用的隔离级别。

## 实施顺序与验收

先建立可持久化的角色实体与角色私有记忆，接入多只独立应用机器人，使每个角色的入口、凭证、任务和回信正确对应；再完成秘书提出建议、招募、交接、合并和解雇的完整生命周期。强隔离执行环境作为明确的能力等级另行验证。

需要验证：不同机器人消息不会串任务；角色不能通过资料接口越域；共同偏好可共享，私有记忆不可默认跨角色读取；秘书按范围获得交付；新增角色不复制全量历史或全部技能；平台未开通时显示准确状态；归档角色保留可导出的积累；受限执行模式确实拒绝越界文件和工具调用。
