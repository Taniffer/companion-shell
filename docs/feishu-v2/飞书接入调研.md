# 飞书接入调研与 V2 交互决策

核查日期：2026-11-18。范围：当前伴随 MVP 源码、飞书官方文档与官方 Node SDK、Botmux 当前公开源码。这里只读调研，没有创建机器人、申请权限、发送测试消息或修改真实飞书配置。

## 建议的接入深度

飞书承担随身沟通、任务查询、必要决策、轻记录和成果交付；Windows / Codex Desktop 负责实际执行；Web 承担全屏任务看板。默认一个秘书，持续的专业需求才开独立角色机器人。用户在任一入口讨论的是同一份任务和资料，切换入口不重新开工。

第一轮应做到**应用机器人 + 常驻菜单 + 原生交互卡与表单 + 独立角色会话 + 明确的任务交接**。飞书原生任务、日历、云文档与多维表格是后续按需启用的扩展，不作为第一轮能否使用的前提。

飞书应用机器人支持单聊、群聊和菜单等能力；自定义 Webhook 机器人主要用于群内推送，不能承担这种双向秘书体验。[机器人概述](https://open.feishu.cn/document/client-docs/bot-v3/bot-overview)、[自定义机器人说明](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)

## 能力与当前实现的差距

“平台可行”指文档或公开实现已确认，不代表本机已接通。当前 MVP 的四个角色仍是一个机器人内的静态角色配置。

| 交互能力 | 当前 MVP | 平台可行性与 V2 决策 |
| --- | --- | --- |
| 与秘书自然聊天、转交 Codex | 已有单机器人消息桥接 | 保留自然语言主线，不要求记命令 |
| 图片、文件、富文本资料 | 已有基础收取与成果发送 | 加入“当前任务附件 / 独立记录”的明确归属与登记回执 |
| 任务运行进度 | 已有简单原位更新卡 | 补齐负责人、真实阶段、更新时间、下一步和操作回执 |
| 卡片按钮、原生表单 | 尚未订阅卡片回调 | 可实现输入、选择、提交与后续更新；作为主交互，而非仅贴网页链接 [卡片组件](https://open.feishu.cn/document/feishu-cards/card-json-v2-components/component-json-v2-overview) |
| 输入框固定菜单 | 当前只有命令入口 | 接入菜单事件，秘书固定“我的任务 / 记一下 / 助理”；专家固定“当前任务 / 我的任务 / 找秘书” [菜单事件](https://open.feishu.cn/document/client-docs/bot-v3/events/menu) |
| 每个专业角色独立机器人 | 未实现动态多机器人 | 每个长期角色绑定独立 app 与会话；临时任务不必建机器人 |
| 自动招募与配置 | 未实现 | 已找到官方扫码建应用、官方配置/发布接口及 Botmux 网页自动化三类路径；详见下节，不可混称已经全自动接通 |
| 解雇、记忆与任务并回 | 目前只有产品方案 | 先停新派单、完成交接再停用外部应用；保留历史与成果 |
| 所有角色任务列表 | Web 有初版数据，飞书仍以命令返回为主 | 飞书卡片提供动态角色筛选、三个状态和分页；详情内再跳负责人 |
| 全屏 HTML 看板 | 电脑本机可用，手机不可直接打开此监听地址 | 手机以原生任务卡为默认；完整看板需另外解决可达性与鉴权 |
| 飞书原生任务/清单/子任务/评论 | 尚未接入 | 可选同步；明确一份主任务事实、双向版本及冲突规则 [任务 V2](https://open.feishu.cn/document/task-v2/overview) |
| 飞书任务智能体 | 尚未注册 | 可让既有应用以智能体身份出现在任务中，不等于创建新聊天机器人 [官方 API Explorer](https://open.feishu.cn/api-explorer?from=op_doc_tab&apiName=register_agent&project=task&resource=agent&version=v2) |
| 云文档、日历、表格等 | 当前桥接示例权限以 IM 为主 | 平台有独立 API，需额外授权和资源访问权限；当前不能标成已连接 [官方能力目录](https://open.feishu.cn/llms.txt) |
| 群聊协作 | 有基础消息与线程处理 | 按实际订阅与权限获取可见消息；私密记忆在单聊继续，不向群卡泄露 |
| 语音、通话、会议助理 | 本轮未实现或验证完整链路 | 不在这版交互中承诺；后续分别核查消息资源、转写与会议权限 |

当前代码证据：`companion-mvp/bridge-kit/src/feishu.mjs` 只注册 `im.message.receive_v1`；`companion-mvp/src/bridge-hooks.mjs` 仍有 `/任务`、`/记`、静态角色切换等入口，`/工作台` 不是已完成的手机看板启动器。这版设计需要新增事件与动作处理，不能只换卡片样式。

## 秘书如何招募独立机器人

### 1. 官方 SDK 已能扫码创建应用

官方 Node SDK 的 `registerApp` 使用 Device Authorization Grant，用户在飞书扫码或打开链接确认后返回应用凭据。可预填名字、头像、描述，并增量申请权限、事件与回调。`addons` 不能配置订阅接收方式等敏感配置，且未知权限名称可能被确认页忽略。因此扫码完成后仍要验收实际权限、菜单、长连接、卡片回调和可用范围。[官方 SDK：一键创建应用](https://github.com/larksuite/node-sdk/blob/main/README.zh.md#一键创建应用)

这是对“只能手动去后台创建”的修正。当前上游能力已经存在；本地桥接还没有接入这一流程，依赖版本与具体租户适用性也需在实现时验证。

### 2. 官方配置与发布接口有适用条件

V7 配置接口支持权限、事件与回调的 WebSocket 接收方式、可见范围等。它要求 `application:application:patch`；应用身份仅能操作自身，用户身份需相应应用管理资格。文档明确仅支持开发者后台创建的自建应用，不能推定 SDK 的 PersonalAgent 创建结果必然适用。[更新应用开发配置](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/application-v7/application-v7/application-config/patch)

另有提交发布接口，但提交成功不等于线上可用；仍需检查发布、审核和最终配置。该接口同样有应用来源限制；用户身份文档列所有者/管理员，不能把“开发者可以改配置”直接推成“开发者一定能发布”。[提交应用发布](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/application-v7/application-v7/application-publish/create)

### 3. Botmux 的网页自动化确实有借鉴价值

当前 Botmux 主线复用飞书网页登录态完成创建、读取凭据、配置权限/事件/重定向、创建版本与发布；SDK 扫码注册作为备选。它说明“助手操作后台把配置做完”是可行的产品方向，但网页会话与官方 API 是两条不同的路径，仍受账号权限、登录态、页面变化和租户审核规则约束。[Botmux 创建与配置源码](https://github.com/deepcoldy/botmux/blob/master/src/setup/open-platform-automation.ts)、[SDK 注册封装](https://github.com/deepcoldy/botmux/blob/master/src/setup/register-app.ts)

产品流程应统一为：**提出招募建议 → 用户同意职责与交接 → 开通应用 → 处理平台必要确认 → 核验真实可收发 → 交接 → 打开独立会话**。中途失败显示还差哪一步，并保留已完成进度；不让用户重新描述招募需求。

## 解雇、停用与删除要分开

内部角色退休可以由伴随完成：不再派新任务、把在途工作带到可交接状态、接回未完成任务、去重记忆、保留资料出处与成果。外部应用的停用有官方管理接口：`enable:false`，需企业应用管理权限 `admin:app.enable:write`；不是普通机器人消息权限自然附带的能力。[启用/停用应用](https://open.feishu.cn/document/application-v6/admin/update)

网页也有管理员停用路径。永久删除属于另一步，不能用“停用成功”冒充“机器人及其历史消息都已删除”。这一轮没有验证当前账号的删除资格，也没有执行任何停用或删除。[管理员移除或停用应用](https://www.feishu.cn/hc/zh-CN/articles/327048548457-管理员移除或停用应用)

交互默认“并回秘书并移除角色”：先可靠交接，再退出活动角色入口，并按可用权限停用应用。外部停用失败单列待处理、允许重试，不丢任务，不恢复第二个执行者。永久删除只有在平台支持、权限核验并确认具体对象后再作为后续动作。

## 多机器人之间怎样接续与隔离

每个 app 的 `open_id` 不通用。角色机器人需要自己的用户绑定；`union_id` 仅在同开发商范围可跨应用关联，取得与匹配都要核验。不同 bot 也不能默认读取彼此私聊历史，历史接口受会话成员、权限与可见范围约束。[用户标识说明](https://open.feishu.cn/document/im-v1/buzz-messages/buzz-overview)、[获取历史消息](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/im-v1/message/list)

因此上下文靠伴随维护的任务、授权资料和交接摘要接续。先选中目标任务并登记交接，再打开专业机器人会话；不是指望一个跳转链接自动复制全部聊天。秘书能管理委托范围内的团队，专家仅获取与其任务有关的资料。当前同一 Windows 账号执行仍属于逻辑隔离，不是独立的系统安全边界。

角色知识与技能按需检索，秘书并回的是持续资产与索引，不是把全部技能全文永久放入每次对话。专业会话处理过的决策同步到秘书总览即可；避免多个机器人重复追问和刷未读。

## 不自建远程服务器，哪些事情仍能做

本机主动连飞书的 WebSocket，可接收事件与卡片回调，不要求自己提供公网回调服务器。收到按钮动作后应在 3 秒内响应：先校验并可靠登记动作，再反馈已收到；模型执行和后续卡片更新异步进行。[回调概述](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/callback-overview)、[长连接接收回调](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/receive-and-handle-callbacks)

这个模型仍需要 Windows 在线才能接收并执行新动作。回调失败没有补推机制；消息事件的重试也不能当成无限离线邮箱。当前桥接没有完整离线历史对账，不承诺电脑关机数天后自动无损接续。已经登记到本机的动作可恢复执行；没有收到回执的按钮点击只能显示失败/待重试，不能显示“已成功排队”。

原生卡片与已发送文件能由飞书客户端查看，不依赖手机打开电脑的 localhost。全屏 HTML 看板另需手机可达地址与鉴权；WebView、AppLink 或小程序本身不会把手机的 `127.0.0.1` 变成电脑。未来可以增加局域网/设备互联的看板入口，这不应阻塞本轮原生交互。

## 卡片设计的真实边界

Card JSON 2.0 需要客户端 7.20 及以上，目前只支持共享更新卡，交互与更新时间统一为 14 天。私人内容默认发单聊；群卡只放可共享的信息。长期任务通过固定菜单获取新卡，旧卡作为历史；回调再核对业务版本，不能让旧决定覆盖新状态。[JSON 2.0 说明](https://open.feishu.cn/document/feishu-cards/card-json-v2-breaking-changes-release-notes)

卡片支持打开链接和请求回调，可按电脑、Android、iOS 设置不同跳转。打开专业机器人会话的入口可做，但具体端行为、应用可用范围和身份绑定仍需实机验收。[卡片交互](https://open.feishu.cn/document/feishu-cards/configuring-card-interactions)、[打开机器人会话说明](https://open.feishu.cn/document/develop-robots/add-bot-to-external-group)

“提交并继续”表达业务输入，不能代替 Codex、Windows 或网页所要求的系统授权。需要去电脑处理时提供清楚的下一步，不制造一个功能更强但实际无效的“同意”按钮。

## 下一轮实施顺序与验收

1. 先做一个秘书的菜单、卡片回调、表单、动作持久化与重复提交保护。验收在线、掉线、超时、旧卡、重复点击；每个操作有明确回执。
2. 补任务卡与本机看板的同一份任务事实；详情、当前任务、资料批次与结果发送互相接续。验收不重复建任务、附件归属正确、手机版不出现 localhost 死链。
3. 接入招募状态机与独立机器人：官方扫码路径先验证；适用的 API 自动配置，必要时由登录后的浏览器完成后台步骤。验收逐个 bot 的 owner 绑定、可见性、发布、菜单、长连接、回调和交接，失败能继续。
4. 完成解雇交接与平台停用，验收不丢资料、不双执行、晚到结果归档、停用失败可恢复。之后再按需接原生任务、日历与云文档。
