# 0.2 实现与长期方案的关系

0.2 把原 0.1 交互扩展为任务看板、角色会话、原生飞书卡片、招募建议、角色交接/并回与 Android 悬浮微面板。原始产品方案、技术方案和 Image Gen 图稿保留为历史与长期设计，具体实现和验收以 README、验证记录为准。

## 内部工作接口

模型继续使用官方 Codex Desktop。默认 CLI 在当前任务目录 `.companion/requests` 留下请求，本机协调器处理并写回执；不需要模型访问本机网络。工作凭证只属于当前任务/角色/generation，目录内有忽略规则，不能把它加入 Git。HTTP 工作接口保留给调试，需显式 `--transport http`。

请求 UUID 跨重试保持一致；提交状态、角色建议和委派都按同一编号去重。工作接口不能替用户确认完成，也不能直接决定招募或停用平台机器人。专业角色不能继续转包。

## 角色与同一任务

业务任务、执行 job、角色原生会话分别保存。任务交接保持编号，交换明确资料、要求、摘要和成果；秘书与专业角色保持各自原生会话和工作目录。秘书收到相关专业公开交付用于汇总，不把自己的整段私人聊天注入专业角色。

解雇先封住接单，核实全部在途会话，逐项移交、合并带出处的记忆与技能登记，再尝试平台停用。内部迁移与平台状态分开；平台失败可重试，不丢资料。部分交接失败时保留待恢复状态。

## 飞书配置的真实边界

SDK 一键开通支持本人确认后创建应用及申请消息、事件、回调；菜单仍需独立配置与发布。V7 支持范围以具体应用实际返回为准，不能凭 `PersonalAgent` 名称猜测来源。创建渠道限制不能通过反复追加权限解决。

长连接、用户绑定、菜单、卡片回调、提交发布和平台停用分别记录。卡片操作先持久化并快速回执，随后执行；旧版本表单、跨 app 用户和越界任务被拒绝。账号确认和真实点击尚未完成的项目，在验证记录中列为待验收。

## 后续

设备间对等同步、iOS、统一定时任务视图、自动记忆候选与技能治理继续保留在完整技术方案与产品路线图。当前是本机协调的开发者 MVP。

0.2.1：用户在任一入口修改业务状态或交接负责人时，已有飞书任务卡也会刷新；明确续聊会自动重新打开并取消归档，保持同一任务与原生会话。Android 保持 0.2.0。
